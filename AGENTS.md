# AGENTS.md

## Deviations from the shared plugin architecture

- **`src/platform-ex.ts` is the single place the plugin casts `Platform`.** `Platform.version` (the APP version) and `Platform.build` (the INSTALLER version) are populated by Obsidian at startup — `app.js:226329-226330` — but `PlatformEx` in `obsidian-typings` declares neither. Every read of them, of `process.versions.electron`, and of the two `ipcRenderer.sendSync` probes goes through this one module, so there is exactly one cast in the plugin. When the typings declare them, the local `PlatformVersions` interface is deleted and the casts become plain reads; nothing else changes.
- **`ipcRenderer.sendSync('insider-build', null)` must keep its `null`.** That channel is read/write: with a boolean it WRITES the setting (`app.js:202189`), and only `null` reads it (`app.js:202186`). A unit test asserts the argument, because the call reads like a stray parameter waiting to be tidied away and tidying it away would silently switch a user's release channel.
- **`MIN_RECOMMENDED_ELECTRON_VERSION` in `src/release-streams.ts` is hard-coded to `28.2.3`**, mirroring the constant Obsidian compiles into its own bundle (`app.js:222745`, compared at `:160712`). There is no API in front of it. It is now a FALLBACK rather than the only source — `resolveElectronStatus` prefers `minRecommendedElectronVersion` from the metadata feed when that records one for the running version — but the constant stays, because the feed records it for almost nothing (only `1.13.0` and `1.13.1` of the whole `1.13.x` line). Re-check it against `obsidian-versions` when a new Obsidian version lands. Note the plugin deliberately does NOT repeat Obsidian's own label for that check — Obsidian calls it "installer version too low" while what it compares is the Electron version, and the panel names Electron.
- **`src/obsidian-metadata-api.ts` is an ENRICHMENT feed, and is kept out of `obsidian-releases-api.ts` because the two have opposite failure contracts.** Every source in `obsidian-releases-api.ts` is Obsidian's own and is fatal on failure: a check that cannot read them does not know the answer. `metadata.json` (`obsidian-integration-testing`, served from `raw.githubusercontent.com`) is a third-party mirror, so `fetchOptionalMetadata` in `update-checker-component.ts` swallows its rejection to `null` while the other three keep failing the check. It is consulted FIRST and never INSTEAD — every resolver reaches the same answer without it that it reached before the feed existed. Two properties force that discipline, both measured 2026-08-30: it **lags** (GitHub had `v1.13.8` while the feed's newest entry was `1.13.7`), and it is **sparse** (`runtimeVersions` on 103 of 325 entries). It is also the plugin's only non-Obsidian runtime dependency, which matters for the community-store submission; enrichment-only is what keeps it off the critical path.
- **The Electron-span half of the notice and the panel was deliberately DARK, and has now LIT UP on its own, with no second pass through this code.** It was written when `ElectronStatus.targetVersion` was `null` for every current Obsidian, `runtimeVersions` being absent from every `1.13.x` metadata entry; nothing guesses and nothing renders "unknown", so the sentence and the span simply did not appear. The feed backfilled the field on 2026-08-30 and the branch is live: measured 2026-09-03 against it, `1.13.4` carries `electron: 43.1.1` and `1.13.7` carries `43.3.0` (106 of 325 entries now have `runtimeVersions`, newest `1.13.7`), and the pinned capture run renders both "Your Electron version 43.1.1, latest installer has Electron version 43.3.0" and the collapsed "2 Electron releases in between" — `images/screenshots/screenshot-desktop-2.png` is the frame. It stays dark where the feed is still sparse: `1.14.0` has no entry, so someone on the newest Catalyst build sees no span. The branches remain covered by fixture-driven unit tests (`electron-span.test.ts`, `update-details-modal.test.ts`); `update-actions.cross-platform.integration.test.ts` records why it does not assert them.
- **`https://releases.electronjs.org/releases.json` is 1.28 MB, so it is fetched ONLY when the details modal is opened** — never on the hourly check. `src/electron-releases-api.ts` has exactly one caller, `UpdateDetailsModal.loadElectronSpan`. The span it feeds is bounded by `MAX_LISTED_ELECTRON_RELEASES` (20) and collapses to one release per major beyond that, because the span reaches **245** stable releases for someone on an old installer — which is precisely this plugin's audience. The number dropped is always rendered; silently truncating 245 links to 12 would read as "that is all of them".
- **The Catalyst gate reads `insider-build` ONE-DIRECTIONALLY, and the wording depends on it.** Obsidian hides and forces the toggle `false` when there is no license (`app.js:202195-202197`), so `true` implies a license while `false` is ambiguous — no license, or licensed with the toggle off. The license itself is unreadable: it lives on the module-private singleton `Nk` (`app.js:66191`), which escapes to neither `window` nor `app`, and the typings expose no `account`. So the gate says what is NEEDED ("needs a Catalyst license, with insider builds switched on in Settings → General") and never what the reader lacks. A unit test asserts the negative. **The gate is also PLATFORM-SHAPED, since 2026-09-20**: `Settings → General` is the desktop About tab, and mobile has neither the tab nor any insider toggle, so the mobile half says the download is reached through Obsidian's insider Discord channels rather than the app store. Established from Obsidian's own early-access page (`https://obsidian.md/help/early-access`, which `https://help.obsidian.md/early-access` 301s to): desktop signs in under `Settings → General → Account` and switches early access on under `Settings → General → App`; mobile claims a Discord badge with the license and reads `#insider-welcome`, which carries "instructions for accessing your download based on your device type" — a TestFlight link on iOS, an APK on Android, both posted in the channel. iOS and Android differ in the ARTIFACT, not in the route, which is why one mobile sentence covers both and nothing reads `isAndroidApp`. Mobile also has a THIRD reader the desktop gate does not — someone already on an insider build, since `checkIsInsiderBuild` answers `null` there and this gate is the only branch the beta stream can take — so the sentence describes the channel rather than telling anyone to go and get on it. It is reached on a phone only when `betaStreamMode` is set to `always`, `auto` resolving through `checkIsInsiderBuild() ?? false`; the unit tests cover it, and the cross-platform suite's mobile leg asserts the absence of `Settings → General` on EVERY row rather than skipping past the gate's.
- **The beta stream is the ONE stream that is not platform-aware, and that is now an established fact rather than an oversight.** `resolveBetaStreamStatus` compares the running app version against `feeds.desktopReleases.beta.latestVersion` — a DESKTOP field — on every platform, while the app stream reads the newest Android release on mobile and the installer stream is `null` there. Obsidian publishes ONE Catalyst version line across desktop and mobile, so the desktop feed's beta version is the mobile reader's version too. Established 2026-09-23 from Obsidian's own `changelog.json` (the feed the plugin already fetches, 490 entries): across the 49 consecutive early-access versions from `1.8.8` (2025-02-25) to `1.14.2` (2026-09-15), every one was published on desktop AND mobile under the same version number on the same day — none carried by one platform and not the other, and no date gap in either direction — and 41 of the 94 mobile early-access entries say so in words, "Includes all new features and bug fixes up to Obsidian Desktop" followed by that same version, the other 53 naming no desktop version rather than a different one. The claim is DATED because the lines genuinely were separate before then: mobile `1.0.2` shipped 2021-07-11 against desktop `1.0.2` on 2022-10-20, two unrelated releases colliding on a number, and the last one-sided early-access version is `1.8.7`, mobile-only on 2025-02-14. **The metadata feed's `desktopCatalyst`/`mobileCatalyst` split is not evidence against it** and was the reason to check: those are two changelog PAGES hanging off one key of `metadata.json`, which is keyed by the bare version, so the changelog URL stays the only thing on this stream that reads the platform. A unit test pins the comparison on Android so that the asymmetry with the app stream cannot be "tidied away"; what would reopen it is a mobile early-access release under a number the desktop beta feed never carried.
- **"Update app only" is a PATH, not a button — `Settings → General → Check for updates`.** The tab's internal id is `about` (`app.js:202140`) while its display name is "General" (`i18n.js`, `about.name`), so user-facing text says General and any code that ever navigates there must use `'about'`. The app's own button is at `app.js:202542`; the three other `buttonCheckForUpdates` call sites are appearance/themes (`:163381`) and Community plugins (`:218431`, `:219139`) and are NOT it. A button was rejected because the real handler is a module-private updater a plugin could only reach by matching LOCALIZED button text in the DOM.
- **The install routes are PLATFORM-SHAPED, and the desktop pair is desktop-only in substance rather than in wording.** `appendInstallRoutes` branches on `isDesktopApp`: desktop gets the two routes above, mobile gets one `Update Obsidian` link to the same platform-aware `getDownloadUrl()`. Both desktop sentences name things Android does not have — there is no installer (which is why the mobile panel omits the installer stream at all), and `Settings → General → Check for updates` is the desktop About tab. Until 2026-09-20 `appendInstallRoutes` took no platform into account and rendered both on mobile, inside `images/screenshots/screenshot-mobile-2.png`, so the defect shipped in the store listing rather than only in the code. Mobile gets ONE route rather than none because these actions are reached only for a stream that HAS an update: suppressing them would announce an update and then offer nowhere to go, and would invert the `hasActions === isUpdateAvailable` invariant the cross-platform suite asserts. The mobile sentence deliberately does NOT name the Play Store — the plugin cannot tell a store install from a sideloaded APK, and someone who has switched automatic updates off is disproportionately the second. The Catalyst gate's own `Settings → General` was the same class of defect on the same platform, fixed later the same day once the research it needed was done; the bullet above records what was established and where the mobile insider route actually goes. `SETTINGS_GENERAL_PATH` now has exactly two users and both decide on `isDesktopApp`, which is what its own ⚠️ says a third would have to do.
- **The notice's links need no dismissal guard.** A `Notice`'s dismiss is a bubble-phase handler a child click reaches, so an interactive child needs `stopPropagation()`. That is for buttons, which must leave the notice standing; these are links, and the notice closing as one is followed is correct. The no-button decision above is what removes the requirement.
- **`src/obsidian-releases-api.ts` caches nothing, on purpose.** One check fetches all its feeds — the three Obsidian ones plus the enrichment feed below — and hands the payloads to the stream resolvers together, so two streams cannot disagree about the state of the same check. A cache would add exactly that failure mode and save nothing at an hourly interval.
- **The changelog for a version with no public release comes from `https://obsidian.md/changelog.json`, not from scraping the HTML index.** The JSON Feed is structured and carries the full history (484 entries as of 2026-08-29) rather than the ~21 the HTML index renders — which matters because a Catalyst-only version has no GitHub release to read a changelog URL from and can be far enough back that the index no longer lists it.
- **`semver` is used at runtime** by `src/release-streams.ts`, to compare versions. Same use as in `obsidian-custom-attachment-location`.
- **No `i18next`; English-only**, as the author's newer plugins are. A plugin that later needs translations reinstates `t` from `obsidian-dev-utils/obsidian/i18n/i18n` AND an `src/i18n/i18next.d.ts` augmenting `CustomTypeOptions`.
- **No `evalInObsidian` closure in this repo may wait on a feed — the waiting happens in Node, via `pollInObsidian`.** A single closure is capped at roughly 30 seconds by whichever transport is driving it: Appium/chromedriver enforces the W3C script timeout and reports the failure as a bare `WebDriverError: script timeout` naming only `AppiumTransport.evaluate`, and the desktop CDP transport enforces its own `commandTimeoutInMilliseconds` (30s). A real check here costs four `requestUrl` feeds, one of them the 484-entry `changelog.json`, and a check that stalls for any reason — a cold emulator whose network is not up yet is the documented one — is killed by that cap before the test's own 90s wait can report anything. That is how the two cross-platform suites came to fail with an error naming only the harness, and to be diagnosed for a day as a broken emulator. Every integration suite therefore keeps its closures to milliseconds of DOM reading and lets `pollInObsidian`'s `start` / `poll` / `until` do the waiting from Node. The harness's own `waitForLayoutReady` is built the same way, for the same reason.
- **A test that opens the details panel must first wait for a check to reach a real answer.** The panel renders whatever the last check resolved, so `executeCommandById('…:check-for-updates')` on an instance that has not finished one opens a modal with no streams in it — and nothing throws. Poll the status bar item until its text stops saying "not checked", THEN open the panel. This is not hypothetical: the Android capture suite, run against the harness's own freshly booted emulator, captured an empty panel and failed with `expected [] to include 'App'`, because on a cold AVD the device has no validated network for roughly its first 80 seconds while every readiness signal the harness gates on has long since cleared. The failure is worse than a timeout — the test runs to completion against a silently empty result — so the wait is what makes the shot mean anything.
- **A desktop test that opens `app.setting` gets its settings in the driven window because the HARNESS turns `settingsPopoutWindow` off — nothing local is needed, and nothing local should be reinstated.** `app.setting` is popout-capable: `shouldUsePopout()` returns `app.vault.getConfig('settingsPopoutWindow')`, and **Obsidian's own default config sets that key to `true`** — verified in the shipped bundles of both `obsidian-1.14.0.asar` (what the harness provisions) and 1.13.7, so it is a long-standing default rather than a new regression. The popout branch is taken whenever `Platform.canPopoutWindow`, i.e. `isDesktopApp && isDesktop` — every desktop run, no mobile one. It creates a real second window, reassigns the `activeWindow` / `activeDocument` globals to it, and the base `Modal.open()` then appends `getRootEl()` (`modalEl`, for a popout) into THAT window's document, leaving the main document with none of the settings UI. Measured 2026-09-03: after `open()` the main document held three `.setting-item-name` rows, all of them the search sidebar's. A suite that only ASSERTS can sidestep this by reading `settingTab.containerEl` — an object reference, wherever it lives — but `screenshots.desktop-capture.integration.test.ts` cannot, because `captureObsidianScreenshot` photographs the main window and a popout yields a frame with no settings in it and no error to say so. **The durable fix landed in the harness: since `obsidian-integration-testing` 12.1.0 it writes `settingsPopoutWindow: false` into every vault it owns**, beside the `alwaysUpdateLinks` it already wrote, so a suite reaching its vault through `getTemporaryVault()` is clear of the popout before it runs. The local `setConfig` call and the `VaultWithPopoutConfig` cast it needed — `obsidian-typings`' `ConfigItem` union omits the key — came out on 2026-09-20. The harness's own `AGENTS.md` section **L48. Headless vault defaults** owns the write and says where it has to land; the one shape that carries no default is a vault built in-worker rather than provisioned by the harness.
- **`app.setting.open()` attaches `containerEl` itself; do not pre-append it.** An earlier `screenshots.desktop-capture.integration.test.ts` appended `app.setting.containerEl` to `document.body` before calling `open()`, on the premise that `open()` returns without attaching and the modal would otherwise build into a detached tree. That premise does not hold for the Obsidian this harness provisions: measured in the same 2026-09-03 run, with the popout suppressed, `document.body.contains(containerEl)` went from `false` before the call to `true` after it, with `modalEl` inside — 1.14.0's `Modal.open()` does `activeWindow.document.body.appendChild(this.getRootEl())`, and the settings modal lazily appends `modalEl` into `containerEl` at open time. The pre-append and its `SettingsModalWithContainer` interface are gone. What actually broke the shot was the popout above, which the pre-append could never have fixed.
- **The screenshot capture project PINS the Obsidian it photographs; the regular test projects do not.** `capture-screenshots:desktop` in `scripts/vitest-config.ts` sets `obsidianVersion: 'public-latest'` and `obsidianInstallerVersion: '1.13.4'`, and `screenshots.desktop-capture.integration.test.ts` asserts the resulting frame (App `Up to date.`, Installer `An update is available.`, the `Update with new installer (recommended)` route). Unpinned, shot 2's CONTENT is whatever the harness happened to boot: the 2026-09-03 recapture ran against the Catalyst `obsidian-1.14.0.asar` and rendered `App Installed: 1.14.0 / Latest: 1.13.7 / Up to date.` — the plugin reporting correctly against the public feed it watches, but a pair that reads as nonsense to a store visitor, with nothing behind and so no action links, and every assertion the suite had at the time still passed. Following the public line keeps the App row current; an installer frozen well below it keeps the Installer row behind on ANY day, because `Latest` only ever moves up. This deliberately overrides the `OBSIDIAN_VERSION` escape hatch `obsidian-dev-utils` honours on `integration-tests:desktop`, for the capture project only — a screenshot taken against an arbitrary version is the defect above, not a feature. When a future `public-latest` asar stops booting on the pinned shell the harness throws `IncompatibleInstallerVersionError` from version resolution, before launch: raise the installer pin then. The Android half takes no such pin because the Appium transport exposes no version knob and the mobile panel has no installer stream.
- **A capture run ALWAYS rewrites all four PNGs, so a dirty tree after `npm run capture:screenshots` is not a finding.** The details panel prints a real `Last checked <wall clock>`, and the frames carry compression noise on top of that: mobile shot 1 is the settings panel — no clock in it — and still moved 136378 → 136381 between two runs of an unchanged plugin. Byte-stability is therefore unreachable, and blanking the timestamp would buy a frame of a panel state the plugin never renders while still leaving the tree dirty; the decision (owner, 2026-09-03) is to keep the real timestamp and guard the frame's CONTENT with assertions instead. Judge a recapture on what the shot SHOWS, and restore any whose only difference is the clock or the noise.

# AGENTS.md

## Deviations from the shared plugin architecture (G51)

- **`src/platform-ex.ts` is the single place the plugin casts `Platform`.** `Platform.version` (the APP version) and `Platform.build` (the INSTALLER version) are populated by Obsidian at startup — `app.js:226329-226330` — but `PlatformEx` in `obsidian-typings` declares neither. Every read of them, of `process.versions.electron`, and of the two `ipcRenderer.sendSync` probes goes through this one module, so there is exactly one cast in the plugin. When the typings declare them, the local `PlatformVersions` interface is deleted and the casts become plain reads; nothing else changes. Tracked as `T681-P8`.
- **`ipcRenderer.sendSync('insider-build', null)` must keep its `null`.** That channel is read/write: with a boolean it WRITES the setting (`app.js:202189`), and only `null` reads it (`app.js:202186`). A unit test asserts the argument, because the call reads like a stray parameter waiting to be tidied away and tidying it away would silently switch a user's release channel.
- **`MIN_RECOMMENDED_ELECTRON_VERSION` in `src/release-streams.ts` is hard-coded to `28.2.3`**, mirroring the constant Obsidian compiles into its own bundle (`app.js:222745`, compared at `:160712`). There is no API in front of it. It is now a FALLBACK rather than the only source — `resolveElectronStatus` prefers `minRecommendedElectronVersion` from the metadata feed when that records one for the running version — but the constant stays, because the feed records it for almost nothing (only `1.13.0` and `1.13.1` of the whole `1.13.x` line). Re-check it against `obsidian-versions` when a new Obsidian version lands. Note the plugin deliberately does NOT repeat Obsidian's own label for that check — Obsidian calls it "installer version too low" while what it compares is the Electron version, and the panel names Electron.
- **`src/obsidian-metadata-api.ts` is an ENRICHMENT feed, and is kept out of `obsidian-releases-api.ts` because the two have opposite failure contracts.** Every source in `obsidian-releases-api.ts` is Obsidian's own and is fatal on failure: a check that cannot read them does not know the answer. `metadata.json` (`obsidian-integration-testing`, served from `raw.githubusercontent.com`) is a third-party mirror, so `fetchOptionalMetadata` in `update-checker-component.ts` swallows its rejection to `null` while the other three keep failing the check. It is consulted FIRST and never INSTEAD — every resolver reaches the same answer without it that it reached before the feed existed. Two properties force that discipline, both measured 2026-08-30: it **lags** (GitHub had `v1.13.8` while the feed's newest entry was `1.13.7`), and it is **sparse** (`runtimeVersions` on 103 of 325 entries). It is also the plugin's only non-Obsidian runtime dependency, which matters for the community-store submission (`T720-P41`); enrichment-only is what keeps it off the critical path.
- **The Electron-span half of the notice and the panel is deliberately DARK, and lights up on its own.** `ElectronStatus.targetVersion` is `null` for every current Obsidian, because `runtimeVersions` is absent from every `1.13.x` metadata entry — tracked as `T717-P2`. Nothing guesses, and nothing renders "unknown"; the sentence and the span simply do not appear. When `T717-P2` backfills the field they start rendering with no second pass through this code. Their branches are covered by fixture-driven unit tests (`electron-span.test.ts`, `update-details-modal.test.ts`), which is the only way to exercise them today; `update-actions.cross-platform.integration.test.ts` records why it does not assert them.
- **`https://releases.electronjs.org/releases.json` is 1.28 MB, so it is fetched ONLY when the details modal is opened** — never on the hourly check. `src/electron-releases-api.ts` has exactly one caller, `UpdateDetailsModal.loadElectronSpan`. The span it feeds is bounded by `MAX_LISTED_ELECTRON_RELEASES` (20) and collapses to one release per major beyond that, because the span reaches **245** stable releases for someone on an old installer — which is precisely this plugin's audience. The number dropped is always rendered; silently truncating 245 links to 12 would read as "that is all of them".
- **The Catalyst gate reads `insider-build` ONE-DIRECTIONALLY, and the wording depends on it.** Obsidian hides and forces the toggle `false` when there is no license (`app.js:202195-202197`), so `true` implies a license while `false` is ambiguous — no license, or licensed with the toggle off. The license itself is unreadable: it lives on the module-private singleton `Nk` (`app.js:66191`), which escapes to neither `window` nor `app`, and the typings expose no `account`. So the gate says what is NEEDED ("needs a Catalyst license, with insider builds switched on in Settings → General") and never what the reader lacks. A unit test asserts the negative.
- **"Update app only" is a PATH, not a button — `Settings → General → Check for updates`.** The tab's internal id is `about` (`app.js:202140`) while its display name is "General" (`i18n.js`, `about.name`), so user-facing text says General and any code that ever navigates there must use `'about'`. The app's own button is at `app.js:202542`; the three other `buttonCheckForUpdates` call sites are appearance/themes (`:163381`) and Community plugins (`:218431`, `:219139`) and are NOT it. A button was rejected because the real handler is a module-private updater a plugin could only reach by matching LOCALIZED button text in the DOM.
- **The notice's links need no G54 dismissal guard.** G54 records that a `Notice`'s dismiss is a bubble-phase handler a child click reaches, so an interactive child needs `stopPropagation()`. That is for buttons, which must leave the notice standing; these are links, and the notice closing as one is followed is correct. The no-button decision above is what removes the requirement.
- **`src/obsidian-releases-api.ts` caches nothing, on purpose.** One check fetches all its feeds — the three Obsidian ones plus the enrichment feed below — and hands the payloads to the stream resolvers together, so two streams cannot disagree about the state of the same check. A cache would add exactly that failure mode and save nothing at an hourly interval.
- **The changelog for a version with no public release comes from `https://obsidian.md/changelog.json`, not from scraping the HTML index.** The JSON Feed is structured and carries the full history (484 entries as of 2026-08-29) rather than the ~21 the HTML index renders — which matters because a Catalyst-only version has no GitHub release to read a changelog URL from and can be far enough back that the index no longer lists it.
- **`semver` is used at runtime** by `src/release-streams.ts`, to compare versions. Same use as in `obsidian-custom-attachment-location`.
- **No `i18next`; English-only**, as the fleet's newer plugins are. A plugin that later needs translations reinstates `t` from `obsidian-dev-utils/obsidian/i18n/i18n` AND an `src/i18n/i18next.d.ts` augmenting `CustomTypeOptions`.
- **No `evalInObsidian` closure in this repo may wait on a feed — the waiting happens in Node, via `pollInObsidian`.** A single closure is capped at roughly 30 seconds by whichever transport is driving it: Appium/chromedriver enforces the W3C script timeout and reports the failure as a bare `WebDriverError: script timeout` naming only `AppiumTransport.evaluate`, and the desktop CDP transport enforces its own `commandTimeoutInMilliseconds` (30s). A real check here costs four `requestUrl` feeds, one of them the 484-entry `changelog.json`, and a check that stalls for any reason — a cold emulator whose network is not up yet is the documented one — is killed by that cap before the test's own 90s wait can report anything. That is how the two cross-platform suites came to fail with an error naming only the harness, and to be diagnosed for a day as a broken emulator (`T796-P41`). Every integration suite therefore keeps its closures to milliseconds of DOM reading and lets `pollInObsidian`'s `start` / `poll` / `until` do the waiting from Node. The harness's own `waitForLayoutReady` is built the same way, for the same reason.
- **A test that opens the details panel must first wait for a check to reach a real answer.** The panel renders whatever the last check resolved, so `executeCommandById('…:check-for-updates')` on an instance that has not finished one opens a modal with no streams in it — and nothing throws. Poll the status bar item until its text stops saying "not checked", THEN open the panel. This is not hypothetical: the Android capture suite, run against the harness's own freshly booted emulator, captured an empty panel and failed with `expected [] to include 'App'`, because on a cold AVD the device has no validated network for roughly its first 80 seconds (`T934-P2`) while every readiness signal the harness gates on has long since cleared. The failure is worse than a timeout — the test runs to completion against a silently empty result — so the wait is what makes the shot mean anything.
